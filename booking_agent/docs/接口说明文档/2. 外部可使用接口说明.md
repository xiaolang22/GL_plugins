## booking agent 接口整理

| 接口                    | 输入参数                                                                             | 输出参数                                                                                  | 内部业务逻辑                                                                            |
| --------------------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------- |
| `POST /create_sheet`  | `date`, `sessions`, `operator_userid`, `operator_name`                           | `content`, `date`, `weekday`, `created_count`, `sheets`                               | 先校验日期合法性和表名是否重复；读取第一个文档和模板；按日期/场次创建企业微信子表；调用模板填充函数补字段、记录、分组；最后同步到 SQLite 并写日志     |
| `POST /delete_sheet`  | `date+session` 或 `sheet_id` 或 `sheet_name`, `operator_userid`, `operator_name`   | `content`, `sheet_id`, `sheet_name`, `deleted_at`, `located_by`                       | 先以日期+场次定位目标工作表；校验不能删模板、不能删最后一张子表；远端调用企业微信删除接口；本地删除 SQLite 记录；写入日志                 |
| `POST /update_record` | `date`, `session`, `seat_name`, `fields`, `operator_userid`, `operator_name`     | `content`, `sheet_name`, `seat_name`, `record_id`, `updated_fields`, `booking_status` | 按日期+场次定位工作表，再按座位名定位记录（座位名字唯一）；根据字段更新自动计算 `是否已订`；将字段值转换为企业微信智能表格 API 格式；执行更新；最后写日志 |
| `POST /add_record`    | `date`, `session`, `seat_name`, `fields`（可选）, `operator_userid`, `operator_name` | `content`, `sheet_name`, `seat_name`, `record_id`, `fields`, `booking_status`         | 校验 seat_name 和字段白名单；默认补齐座位类型、是否已订等字段；检查座位名是否重复；创建新记录；自动更新订座状态；写日志                 |
| `POST /delete_record` | `date`, `session`, `record_id` 或 `seat_name`, `operator_userid`, `operator_name` | `content`, `sheet_name`, `deleted_record_id`, `seat_name`, `deleted_at`               | 定位工作表；按 `record_id` 或 `seat_name` 找到目标记录；调用企业微信 delete_records 删除；删除成功后记录日志       |
| `POST /query_records` | `date`, `session`                                                                | `content`, `sheet_name`, `total`, `booked_count`, `available_count`                   | 读取目标工作表全部记录；提取字段值；统计已订/未订数；输出 Markdown 表格文本，供机器人或用户查看                             |
### 统一理解

这几个接口的核心设计是：

1. 以 `date + session` 定位表
   - 例如：2026-09-26 + dinner
2. 以 `seat_name` 或 `record_id` 定位记录
3. 由 `composite.py` 统一做业务编排
4. 真正的微信操作都在 `api_wework.py` 中完成
5. 状态同步写入 SQLite，日志记录在 `db.py`

---

### 关键业务规则

#### 1. 订座状态自动计算
在 `update_record` 和 `add_record` 中，字段满足以下任一条件时，自动设置 `是否已订 = 已订座`：

- `客人称呼`
- `客人电话`
- `人数`
- `留菜`
- `留位人`

如果这些字段全部为空，则自动变成：

- `是否已订 = 未订座`

这条规则是代码中最核心的业务逻辑之一。

#### 2. 只允许操作本项目的工作表
删除工作表时，代码会做严格校验：

- 不能删模板工作表
- 不能删最后一张子表
- 不能跨文档删除

#### 3. 模板复制机制
`create_sheet` 并不是手工建表，而是基于模板复制：

- 先读模板表内容
- 复制字段结构和记录样式
- 在新工作表中填充默认座位数据
- 统一分组和展示规则

## 1) /create_sheet

### 输入参数
请求体 JSON，核心字段：
- date：目标日期，支持 YYYY-MM-DD 或 MM-DD
- sessions：可选，场次列表，如 ["lunch","dinner"]、["午市","晚市"] 或单个字符串
- operator_userid：操作人微信 userid
- operator_name：操作人名称
示例：
- {"date":"2026-09-26","operator_userid":"xxx","operator_name":"yyy"}
- {"date":"9-26","sessions":["dinner"],"operator_userid":"xxx","operator_name":"yyy"}
### 输出参数
返回对象：
- content：自然语言结果
- date：日期
- weekday：星期
- created_count：创建张数
- sheets：列表，每项包含
  - sheet_name
  - sheet_id
  - session_type
  - status
### 内部业务逻辑
一句话总结：它是“按日期 + 场次，复制模板构造一张或多张空白订座表”。
对应函数：create_any_sheet_and_sync，见 `composite.py:754-908`
逻辑分为 4 步：
1. 解析日期和场次
   - 通过 _parse_date_str 和 _normalize_sessions 处理各种输入格式
   - 生成工作表名，如 9-26晚市周六

2. 前置校验
   - 不允许创建过去日期
   - 不允许创建已存在的 sheet_name
   - 通过 db.get_existing_sheet_names 进行重名校验

3. 获取模板和文档
   - 从数据库读第一个 doc_id
   - 从数据库读第一个模板 template_content
   - 若不存在，直接报错

4. 批量创建与填充
   - 对每个目标日期/场次调用 add_sheet 创建远端子表
   - 通过 _fill_sheet_from_template 填充字段、记录、分组规则
   - 调用 db.insert_sheet 写本地 SQLite
   - 记录日志

## 2) /delete_sheet

### 输入参数
三种定位方式优先级：
1. date + session
   - {"date":"2026-09-26","session":"dinner"}
2. sheet_id
   - {"sheet_id":"xxxx"}
3. sheet_name
   - {"sheet_name":"9-26晚市周六"}
可选：
- operator_userid
- operator_name
### 输出参数
返回对象：
- content：自然语言结果
- sheet_id
- sheet_name
- deleted_at
- located_by：定位方式，date_session / sheet_id / sheet_name
### 内部业务逻辑
一句话总结：删除一个已存在的日常工作表，且保证不会误删模板，也不会删空文档。

对应函数：delete_sheet_and_sync，见 `composite.py:909-1089`
逻辑分为 4 步：
1. 定位表
   - 优先按 date + session 找工作表
   - 如没有，再按 sheet_id
   - 最后按 sheet_name

2. 安全校验
   - 不能删除模板工作表
   - 不能删除数据库中不属于第一个 doc 的表
   - 不能删除最后一张子表（企业微信限制）

3. 远端删除
   - 调用 api_wework.get_sheet_list
   - 检查远端子表数
   - 调用 api_wework.delete_sheet 删除企业微信中的子表

4. 本地同步
   - 调用 db.delete_sheet_by_id 删除 SQLite 记录
   - 写入操作日志

## 3) /update_record

### 输入参数
核心字段：
- date：日期
- session：场次
- seat_name：座位名称，用于定位记录
- fields：要更新的字段字典
- operator_userid
- operator_name
允许更新字段（英文 key）：
- seat_type
- seat_capacity
- seat_remark
- guest_name
- guest_phone
- guest_count
- reserved_dishes
- reserved_by
禁止更新字段：
- seat_name
- booking_status
示例：
- {"date":"2026-09-26","session":"dinner","seat_name":"北京房","fields":{"guest_name":"张三","guest_phone":"13800138000","guest_count":"8"}}
### 输出参数
返回对象：
- content：自然语言提示
- sheet_name
- seat_name
- record_id
- updated_fields：实际更新字段
- booking_status：已订座 / 未订座
### 内部业务逻辑
一句话总结：它是“按座位定位并更新订座信息，同时自动维护是否已订状态”。

对应函数：update_record_and_sync，见 `composite.py:1093-1258`
核心逻辑：
1. 定位工作表和记录
   - 根据 date + session 拼出 sheet_name
   - 根据 seat_name 查找对应 record_id

2. 订座自动状态计算
   - 规则：只要 guest_name / guest_phone / guest_count / reserved_dishes / reserved_by 任一字段非空，则 booking_status 自动设为 已订座
   - 若全部为空，则自动设为 未订座
   - 判断基于更新后的最终值

3. 构造更新 payload
   - 读取工作表字段 map
   - 将字段值按企业微信 API 格式包装
   - 自动追加 是否已订 字段

4. 调用微信 API
   - api_wework.update_records 执行更新

5. 写日志
   - 记录哪位操作人、更新了什么字段、更新后状态

## 4) /add_record

### 输入参数
核心字段：
- date
- session
- seat_name：新座位名称
- fields：可选，允许只传座位属性字段
  - seat_type
  - seat_capacity
  - seat_remark
- operator_userid
- operator_name
示例：
- {"date":"2026-09-26","session":"dinner","seat_name":"VIP1","fields":{"seat_type":"房间","seat_capacity":"10","seat_remark":"靠窗"}}
### 输出参数
返回对象：
- content
- sheet_name
- seat_name
- record_id
- fields：最终写入的字段
- booking_status
### 内部业务逻辑
一句话总结：它是“新增一个新座位记录”，主要用于创建空座位，不负责客人信息填写。

对应函数：add_record_and_sync，见 `composite.py:1260-1414`
核心逻辑：
1. 定位工作表
   - 根据 date + session 找到对应 sheet

2. 校验输入
   - seat_name 必填
   - 只允许传座位属性字段，不允许传客人信息字段
   - 如 guest_name 等字段会被拒绝

3. 默认值填充
   - 座位名称 = seat_name
   - 座位类型默认 = 大厅
   - 是否已订默认 = 未订座

4. 订座状态推导
   - 如果客人相关字段非空，则 booking_status = 已订座
   - 否则 = 未订座

5. 重复校验
   - 检查当前表中是否已有相同 seat_name
   - 若重复直接报错，避免重复座位

6. 调用微信 API
   - api_wework.add_records 追加记录

7. 写日志

---
## 5) /delete_record

### 输入参数
两种定位方式：
1. record_id
   - {"date":"2026-09-26","session":"dinner","record_id":"rec123"}
2. seat_name
   - {"date":"2026-09-26","session":"dinner","seat_name":"临时桌A"}
可选：
- operator_userid
- operator_name
### 输出参数
返回对象：
- content
- sheet_name
- deleted_record_id
- seat_name
- deleted_at
### 内部业务逻辑
一句话总结：它是“在指定日期/场次表中删除某一条座位记录”。

对应函数：delete_record_and_sync，见 `composite.py:1416-1555`
核心逻辑：

1. 定位工作表
   - 先根据 date + session 找到 sheet

2. 定位记录
   - 若给了 record_id，直接删
   - 若给了 seat_name，先遍历所有记录找到 matching 的座位名

3. 调用微信 API 删除
   - api_wework.delete_records

4. 更新本地日志
   - 记录删除人、删除时间、删除记录 ID

---

## 6) /query_records

### 输入参数
- date：日期
- session：场次
- operator_userid / operator_name：可选，不是核心参数
示例：
- {"date":"2026-09-26","session":"dinner"}
### 输出参数
返回对象：
- content：格式化的 Markdown 表格文本
- sheet_name
- total：总记录数
- booked_count：已订座数量
- available_count：未订座数量
### 内部业务逻辑
一句话总结：它是“读取一张表的所有订座记录，并返回结构化表格摘要”。

对应函数：query_records_and_sync，见 `composite.py:1557-1686`
核心逻辑：
1. 定位目标工作表
2. 拉取当前页数据，并做分页补齐
3. 解析每条记录中的字段值
4. 统计：
   - 总数
   - 已订座数量
   - 未订座数量
   - 房间/大厅订座数量
5. 组装 Markdown 表格输出
   - 表头为座位名称、容量、备注、客人称呼、客人电话、人数、留菜、留位人、座位类型、是否已订
   - 生成可直接展示给机器人或人看的内容
